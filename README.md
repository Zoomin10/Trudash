# Club volunteers update

Adds public signup at the TCM frontend /volunteers and a Club volunteers menu in TruDash. Existing member registration and Stripe billing remain intact. Based on the repository commits in the accompanying base-commit files.

## Install and deploy

Copy the contents of TotalClubManagement into the matching repository, and TruDash into the matching repository. These are selected changed files, not replacement repositories. Preserve any later edits when merging the supplied patches. Do not copy tests, patch files or this README into application folders.

Deploy to Development first. Commit the new migration as well as the Prisma schema. Deploy TCM backend first, with your existing Prisma generate build and `npx prisma migrate deploy` pre-deploy command, then TCM frontend and TruDash. There are no new packages. Do not run migrate dev against the Railway production database. The supplied SQL is generated by Prisma against the previous committed schema; do not create an additional migration for the same tables.

The migration creates ClubVolunteer, VolunteerAcceptance and VolunteerChange without changing member or billing tables. The existing deployment must run migrations before it serves volunteer requests.

## Required configuration

Keep all existing membership integration variables. Club volunteers currently uses the same enabled feature flag and administrator allowlist as Membership pilot:

TruDash service:

MEMBERSHIP_PILOT_ENABLED=true
MEMBERSHIP_PILOT_ADMIN_EMAILS=@wwfc.org.uk
VOLUNTEER_SUPER_ADMIN_EMAILS=your-specific-microsoft-login@wwfc.org.uk

The Super Admin bootstrap list accepts explicit email addresses only, separated by commas. Domain-wide values such as @wwfc.org.uk do not grant Super Admin. The identity must also qualify under the existing membership administrator allowlist. Keep the shared secret unchanged on both services.

## Included agreement documents

Both supplied documents identify themselves as Version 1.0:

- WWFC Volunteer Agreement and Conduct Standards (VOLUNTEER, version 1.0).
- POL003 Coach Code of Conduct (COACH, version 1.0).

The complete body wording, lists and table text are bundled in backend/src/content/volunteerAgreements.json. Original unmodified Word documents are served by the TCM frontend under /agreements with versioned filenames. The public form displays the acknowledgement wording from each supplied document, plus download links before and after successful submission. Acceptance stores the full wording, version and timestamp in the database.

You do NOT need agreement text/version Railway variables for these documents. If you created VOLUNTEER_AGREEMENT_VERSION, VOLUNTEER_AGREEMENT_TEXT, COACH_CODE_VERSION or COACH_CODE_TEXT while following the first package's instructions, remove them to use the included documents. Paired text/version variables remain supported as overrides, but a partial override blocks that agreement and overrides do not link to the bundled original, to avoid presenting the wrong copy.

When publishing a revised agreement, change its version, update its bundled text and acknowledgement, and add its new original download. Retain the old original at its existing versioned URL so volunteers retain access to their accepted copy. Never change the content of a published version without a new version number.

This is a complete replacement for the earlier Club-volunteers-update package. The database schema and migration are the SAME; there is no second agreement migration to run. If you already copied the earlier package, the new/changed agreement-related files are backend/src/content/volunteerAgreements.json, backend/src/services/volunteerService.js, frontend/src/VolunteerSignup.jsx and both files in frontend/public/agreements. If not, copy both repository folders as instructed above.

FRONTEND_URL remains the TCM public frontend origin. The public registration URL in TruDash uses TCM_REGISTRATION_URL with /volunteers.

## Behaviour

Volunteer signup: first/last name, email, telephone, optional team, requested roles, explicit acceptance. Requested roles are separate from assigned roles. Signup emails are normalised; duplicate email submissions do not overwrite records or disclose existing details. The club should handle requested amendments administratively.

Club roles: Committee Member, Trustee, Team Manager, Team Coach, Assistant Coach, Marketing, Events, Social Media Manager, Social Impact Manager, Fundraising Manager, Treasurer, Club Secretary, Chair, Vice-Chair, Facility Liaison Manager. Multiple roles may be requested and assigned.

Football roles: Team Manager, Team Coach and Assistant Coach require both agreements. Other roles require the Volunteer Agreement. Activation requires at least one assigned role and all currently required agreements. Missing agreement status also reflects requested football roles.

Management: search and filter, contact details, requested and assigned roles, internal notes, review status, versioned acceptance history. Updates and link creation are audited in VolunteerChange. Concurrent stale updates are rejected; refresh the profile before retrying.

None/Admin/Super Admin are separate access labels, not public signup options. The existing domain/email allowlist already authorises volunteer managers regardless of their saved access label. Admin does not widen that allowlist or grant rights elsewhere in TruDash. Super Admin adds permission to grant/revoke access labels and edit Super Admin records. Only the bootstrap list or an active, fully accepted volunteer with saved Super Admin can exercise those permissions, and they still need the TruDash allowlist. This feature does not replace TruDash's existing application-wide authentication/authorisation rules.

A later assigned football role may require new acceptance: save the role with Awaiting review, then Create agreement acceptance link. Share this link privately with the volunteer. It is a bearer link valid for 30 days and single use; creating another invalidates the previous link. No emails are automatically sent. The link page does not expose contact details. Review safeguarding/suitability requirements separately before activating volunteers; agreement acceptance is not a check clearance.

No deletion or bulk import is included. Existing volunteers shown elsewhere in TruDash are separate and are not migrated by this update.
